## 4. 核心发现：不能靠调阈值修拒答

本次收尾把每题 top1 相似度打进报告后，第一次有了可判定的数据：

| 题型 | 题 | top1 分 |
|---|---|---|
| 应召回 `BMS.docx` | A01 / A02 / A03 / A06 | 0.5390 / 0.5055 / 0.5673 / **0.4225** |
| 期望空返回 | A04（答案层）/ A05（检索层） | 0.5116 / **0.6359** |

两类区间**完全重叠**，且该拒答的 A05 分数高于所有应召回题。结论：

1. **不存在任何单一 `score-threshold` 能把两类题分开**。调高阈值会先砍掉 A06(0.4225)、A02(0.5055)，而 A05(0.6359) 仍会留下。
2. Recall 1.0000 与拒答 0.0000 是同一根因的两面：`ai_knowledge_store` 实查 **4 行 / 仅 1 个 `doc_id`（`BMS.docx`）**，向量空间里没有第二篇文档可供区分，所有崩岸风险相关问题都只会命中它。
3. A04 与 A05 性质不同：A04「Zd 超过 3m 就算高风险，对吗」是**资料存在但说法不被支持**，应由生成层拒答，检索层返回相关片段不算错；A05「GB 50286 阈值」是**资料根本不存在**，才是检索层该拒答的题。考卷已用 `refusalLayer` 区分，**全口径拒答率仍按旧定义统计两题**，保证与 4A 基线可比。

## 6. 阶段 5 的可判定开工门槛

四条**全部满足**才写混合检索代码，否则收益测不出来：

1. `ai_knowledge_store` ≥ 5 个不同 `doc_id`（当前 1）；
2. D 类题期望文档已入库且标记可检索（当前 0）；
3. `V17` 的 `gin (content gin_trgm_ops)` 索引已手动执行（当前 0 根；`migration/V*.sql` 只留档、不在 Flyway 内）；
4. 4B 复测完成，门禁阈值由实测固化。

阶段 5 的设计要点已定：独立 `HybridRagProperties`（默认 false，不碰 `RagProperties` 11 参构造器）、`KnowledgeService` 6 参重载 + 保留 5 参（不碰 5 处直接 `new`）、sparse SQL 自带权限条件、RRF `k=60`、sparse 失败显式降级 dense-only。开工时按此实施即可。

## 7. 备选方向（不依赖语料）

- **阶段 6 SQL 内权限过滤**：真实安全弱点（无权正文短暂进 JVM）。注意 `SearchDocumentDto` 无 filter 字段，须绕过 SDK 写原生向量 SQL，改动量不小。
- **补一次真实在线检索**：让 `ai_rag_traces` 产生数据，工程层指标才可用。
- **补权威语料**：由用户/领域老师提供规范原文或平台冻结口径，从前端知识库页上传；这是唯一能解开死结的动作。

## 8. 复跑方式

```bash
cd bank-warning-server
mvn -q -pl bank-warning-ai -am test                       # CI 门禁，确定性、零网络
mvn -q -pl bank-warning-ai org.codehaus.mojo:exec-maven-plugin:3.1.0:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=com.yangtze.bankwarning.ai.rag.RagEvalCli \
  -Dexec.args="--jdbc --out target/rag-eval.md"          # 真库效果报告
```

`--jdbc` 的 DashScope key 取环境变量 `DASHSCOPE_API_KEY`，缺失时回落读 `application-local.yml`（或 `--key-file`）；key 不写入报告。
